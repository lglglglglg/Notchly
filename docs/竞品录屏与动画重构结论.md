# 竞品录屏与动画重构结论

分析素材：`Screen-2026-09-05-211850.mp4`，时长 12:07，3024×1964，30 fps。

- 04:43–06:20：NookX / 音乐型刘海工具。展示大尺寸音乐面板、封面、进度、上一曲、播放暂停、下一曲、歌词或信息列表。
- 06:20–07:50：另一款音乐型刘海工具。音乐面板从刘海展开，设置中可调整触发方式、尺寸和媒体来源。

## 共同的流畅动画规律

1. 刘海始终是唯一视觉锚点。动画从屏幕顶部中央开始，左右和向下同时生长，中心不会漂移。
2. 黑色背景是一块连续表面。展开过程中看不到两个窗口交叉淡化，也没有边框突然替换。
3. 外形先动，内容后出现。第一阶段先完成约 60%–80% 的宽高变化；封面、文字和按钮随后淡入并轻微上移。
4. 内容不参与重新排版。封面、标题和控制键看起来一直待在最终位置，只改变透明度、模糊度和很小的缩放。
5. 展开和收起不完全对称。展开约 280–360 ms，带很弱的回弹；收起约 180–260 ms，动作更干净。
6. 动画可被打断。鼠标快速划入、划出时，界面从当前进度反向播放，不会先完成上一个动画再开始下一个。
7. 圆角随尺寸连续变化。紧凑态底部圆角较小，展开态圆角更大，不在状态切换点突然改变。
8. 阴影和背景内容跟随岛体逐渐增强，而不是在最后一帧出现。

## 音乐交互规律

- 待机态只在刘海左右显示封面或来源图标，以及播放动态或时间。
- 待机态并不等于空白黑块：播放器没有内容时仍应保留一个低干扰的功能提示，让首次使用者知道这里可以悬停展开。
- 音乐状态必须在收起后继续更新，否则切歌、暂停或更换播放器时，两翼信息会停留在旧状态或退化成空白。
- 快速活动态显示封面、歌曲名或一行歌词；不会出现所有工具卡片。
- 音乐详情态形成一个完整播放器，至少包含封面、歌曲与歌手、上一曲、播放/暂停、下一曲。
- 表现较好的产品还包含播放进度、时间、音量和歌词。
- 切歌时通常只替换音乐内容，岛体尺寸保持稳定；封面和文字交叉淡化或横向滑动。

## 当前 Notchly 0.2.1 的根本问题

- `NSPanel` 在 compact、preview、expanded 三种固定尺寸之间做窗口动画。
- `NotchIslandView` 根据 phase 条件创建和销毁不同的视图分支。
- phase 在窗口尺寸开始变化前已经切换，因此大量内容会先进入一个过小的窗口，再随窗口一起重新布局。
- AppKit 的窗口插值和 SwiftUI 的 transition 各自计时，无法保证每一帧同步。
- 结果是外形变化、布局变化和内容淡入相互抢帧，视觉上像整块界面突然出现。

## 下一版动画架构

1. 使用一个固定为最大展开尺寸的透明 `NSPanel`，整个交互期间不改变窗口 frame。
2. 在 SwiftUI / Core Animation 内只动画岛体的可见宽度、高度、底部圆角和阴影。
3. 用单一连续进度 `expansionProgress`（0...1）驱动所有属性，不再切换三棵独立视图树。
4. compact 与 expanded 是两个稳定停靠点；中间过程只是连续进度，不是可停留的 preview 页面。
5. 内容预先放在最终坐标，通过 mask、opacity、blur、scale 和 offset 分层出现。
6. 音乐预览在外形进度约 0.35 后出现；完整功能在约 0.7 后出现。
7. 使用可中断的 spring 动画；新目标从当前 presentation value 继续，支持快速反向。
8. 固定大窗口在收起时必须允许透明区域鼠标穿透。通过鼠标位置轮询识别刘海触发区，再动态切换窗口的 `ignoresMouseEvents`。
9. 重新逐帧检查音乐类竞品后，悬停不应停在一条容易被实体摄像头遮挡的横向 preview。鼠标首次进入后直接开始完整展开：前半段只做岛体形变，后半段再显示播放器内容，无需第二次点击。

## 下一阶段验收标准

- 录制 60 fps 慢放时，岛体轮廓在展开和收起过程中没有位置跳变。
- 内容不会在小尺寸窗口中挤压、换行或闪现。
- 鼠标快速划入划出至少 10 次，动画均能从当前进度平滑反向。
- 鼠标首次悬停即可自动展开完整播放器，中间过渡帧不显示会被实体刘海遮挡的文字。
- 上一曲、播放/暂停、下一曲不会引起岛体尺寸变化。
- 收起状态下，透明的大窗口区域不会阻挡下方应用点击。
